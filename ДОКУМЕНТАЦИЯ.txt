Главный файл
------------

    main.py

Единственный файл, который нужно запускать.

    python main.py           # меню с выбором по номеру
    python main.py race      # гонка за последним товаром
    python main.py order     # сценарий заказа
    python main.py nplus1    # проблема N+1
    python main.py pages     # пагинация
    python main.py test      # тесты
    python main.py serve     # HTTP-сервис

В PyCharm кнопка «Run» запускает файл без аргументов — появится меню,
в нём можно выбрать пункт по номеру. Либо терминал внизу окна (Alt+F12)
и команда целиком.

Что делает программа
--------------------

Сервис заказов небольшого магазина: каталог товаров, оформление заказа
с резервированием остатков, отмена с возвратом.

Проект собран не вокруг CRUD, а вокруг задач, которые реально возникают
в бэкенде и о которых спрашивают на собеседовании:

  - что происходит, когда два покупателя одновременно берут последний товар;
  - что делать, если клиент повторил запрос из-за обрыва связи;
  - как не сделать 51 запрос к базе там, где хватает двух;
  - как листать каталог, не замедляясь на глубоких страницах;
  - что делать, когда внешний сервис перестал отвечать.

Установка
---------

Ядро написано на стандартной библиотеке — устанавливать ничего не нужно:

    python main.py race

Для тестов нужен pytest, для HTTP-слоя — FastAPI:

    pip install -e ".[dev]"     # pytest, ruff
    pip install -e ".[serve]"   # fastapi, uvicorn, pydantic

Где данные и как их менять
--------------------------

Товары лежат в файле data/catalog.json. Это обычный текст,
правится блокнотом:

    {
      "products": [
        {"sku": "GAME-003", "title": "Коллекционное издание",
         "price_rub": 12999.00, "stock": 1}
      ]
    }

  поле       что значит
  ---------  -----------------------------------
  sku        артикул, должен быть уникальным
  title      название для показа
  price_rub  цена в рублях, можно с копейками
  stock      сколько штук на складе, целое число

Команды:

    python main.py seed              # залить каталог из файла в базу
    python main.py seed --fresh      # снести базу и создать заново
    python main.py catalog           # показать, что сейчас в базе
    python main.py stock GAME-003 42 # изменить остаток одного товара

Где сама база. Файл shop.sqlite3 в корне проекта, создаётся
командой seed. Данные в нём постоянные: оформил заказ — остаток
уменьшился и таким останется до следующего seed.

Почему файл каталога отдельно от базы. Товары — это данные,
а не логика. Их правит человек, который не открывает Python-файлы,
и каждая правка не должна требовать разработчика. База при этом —
рабочее состояние: в ней остатки уже изменены заказами.

Почему seed очищает товары. Файл — источник истины. Иначе
позиция, удалённая из файла, осталась бы в базе навсегда. Если в базе
уже есть заказы, команда откажется чистить: у строк заказа внешние
ключи на товары, и чистка сломала бы историю — для этого случая есть
--fresh.

Проверки при чтении файла. Ошибки собираются все сразу и называют
позицию и поле: пустой артикул, дубль, отрицательный остаток, дробное
количество, битый JSON с номером строки. Иначе файл на сто позиций
чинится по одной строке за запуск.

Отдельная тонкость — цены. В файле рубли, в базе копейки целым
числом. Пересчёт идёт через Decimal, а не int(value * 100):
4999.90 * 100 в двоичной арифметике равно 499989.99999999994,
и int() от него вернёт на копейку меньше.

Демонстрации race, nplus1 и pages работают на временной базе
и твои данные не трогают: им нужны свои условия — товар с остатком 1,
тридцать заказов, двадцать пять позиций. Сценарий заказа можно запустить
и на постоянной базе: python main.py order --db shop.sqlite3.

-------------------------------

    api.py         HTTP: схемы запросов, коды ответов, request_id
       ↓
    services/      бизнес-логика: что можно, что нельзя, в каком порядке
       ↓
    repositories/  доступ к данным: SQL и только SQL
       ↓
    db.py          соединения, транзакции
       ↓
    models.py      доменные типы, не зависят ни от чего

Зависимости идут строго вниз. Практическая польза, а не эстетика:

  - бизнес-логику можно вызвать из CLI, фоновой задачи и теста, не поднимая
    веб-сервер;
  - тесты логики выполняются за миллисекунды, потому что не трогают ни сеть,
    ни диск;
  - заменить sqlite на PostgreSQL — значит написать второй репозиторий,
    не трогая сервисы.

ЧАСТЬ 3. РАЗБОР КЛЮЧЕВЫХ РЕШЕНИЙ

Гонка за последним товаром
--------------------------

Задача. На складе один экземпляр. Два покупателя нажимают «Купить»
в одну миллисекунду. Товар не должен продаться дважды.

Как ломается наивная версия:

    product = get(product_id)            # прочитали: stock = 1
    if product.stock >= quantity:        # проверили: хватает
        update(stock = product.stock - quantity)

Между чтением и записью вклиниваются другие потоки. Все читают
«остаток 1», все проверяют, все списывают. Проверить это можно самому:

    python main.py race

    НАИВНО   продано экземпляров: 11   остаток: 0     ← продали 11 из 1
    АТОМАРНО продано экземпляров: 1    остаток: 0     ← корректно

Решение. Проверка и изменение — одной командой:

    UPDATE products
       SET stock = stock - ?, version = version + 1
     WHERE id = ? AND stock >= ?
    RETURNING id

Условие проверяет сама база в момент записи, под блокировкой строки.
Второй поток либо увидит уже уменьшенный остаток, либо подождёт.

Альтернатива — SELECT ... FOR UPDATE: тоже работает, но требует
держать транзакцию открытой между чтением и записью, то есть дольше
блокировать строку.

Почему RETURNING, а не rowcount
-------------------------------

Это находка проекта, и она стоит отдельного раздела.

Первая версия определяла успех по cursor.rowcount == 1. В один поток
работает. Тест на 20 потоках показал другое: база отработала верно
(остаток ушёл с 1 на 0, изменена ровно одна строка), но rowcount
вернул ноль всем двадцати потокам, включая победителя.

Причина: rowcount берётся из sqlite3_changes(), а эта функция
относится к соединению, а не к курсору. Когда несколько потоков
работают через одно соединение, их вызовы перемежаются, и значение
успевает перезаписаться чужим запросом.

Последствия в проде: сервис решил бы, что резерв не прошёл, откатил
заказ — и товар вернулся бы на склад, хотя покупатель его купил.

RETURNING отдаёт строку в результат самого запроса, привязанный
к своему курсору. Чужой поток на него не влияет. Поддерживается
в sqlite с 3.35 и в PostgreSQL с 8.2.

Отдельный урок: первые прогоны теста были «мигающими» — то проходил,
то падал. Мигающий тест не повод его удалить или пометить skip; это
сигнал, что в коде настоящая гонка.

Соединение на поток
-------------------

Вторая находка проекта, из того же класса, что и rowcount.

Первая версия держала одно соединение sqlite и раздавала его всем
потокам. Причина была в :memory:: у каждого соединения к базе в памяти
своя отдельная база, поэтому потокам пришлось бы делить одно.

На Linux и Python 3.11 это работало. На Windows и Python 3.14 —
падение:

    sqlite3.InterfaceError: bad parameter or other API misuse

Драйвер заметил, что несколько потоков портят внутреннее состояние
соединения. На других версиях он этого не замечал и мог тихо вернуть
мусор — что хуже падения, потому что обнаружится позже и не там.

Решение — то, как устроен любой настоящий сервис: база одна,
соединение своё на каждый поток (threading.local, простейший аналог
пула). Для этого нужна база в файле, поэтому демонстрации и тесты
используют Database.temporary() — временный файл, удаляемый при
закрытии.

Режим :memory: оставлен для однопоточных сценариев: он удобен, но
вызовы в нём выстраиваются в очередь под блокировкой, чтобы не падать.
Настоящей параллельности там нет и быть не может.

Урок: «у меня работает» и «работает» — разные утверждения. Ошибка
в работе с общим состоянием может годами не проявляться на одной
платформе и падать сразу на другой.

Идемпотентность
---------------

Задача. Клиент отправил заказ, связь оборвалась на ответе, клиент
повторил. Заказ не должен создаться дважды.

Решение. Клиент передаёт Idempotency-Key заголовком (так устроены
платёжные API). Повтор с тем же ключом возвращает прежний заказ.

Три тонкости, каждую спрашивают:

1. Уникальность обеспечивает база, а не код. Проверка «сначала
SELECT, потом INSERT» — это гонка: два параллельных запроса оба увидят
пустой результат и оба вставят. Поэтому уникальный индекс:

    CREATE UNIQUE INDEX idx_orders_idempotency
        ON orders (idempotency_key) WHERE idempotency_key IS NOT NULL;

Второй INSERT падает на ограничении — и это правильное поведение,
а не авария.

2. Тот же ключ с другим телом — ошибка, а не старый результат.
Хранится отпечаток запроса (SHA-256 от нормализованного тела). Если
отпечаток не совпал, клиент переиспользовал ключ для другого заказа.
Молча вернуть прежний нельзя: клиент получит не то, что просил,
и не заметит.

3. Отпечаток не зависит от порядка позиций. [(1,2),(3,4)]
и [(3,4),(1,2)] — один и тот же заказ, товары сортируются перед
хешированием.

Транзакции и откат
------------------

Заказ из двух позиций: первая есть, второй не хватает. Если бы резервы
шли вне одной транзакции, первая позиция осталась бы списанной — товар
исчез бы со склада, не будучи проданным. Такие «потери» ищут неделями.

Всё оформление идёт в одной транзакции, и откат возвращает остатки
автоматически — без ручной компенсации.

BEGIN IMMEDIATE вместо обычного BEGIN. Обычный BEGIN берёт
блокировку записи лениво, при первом UPDATE: две транзакции успевают
начаться и почитать, а проигравшая получает «database is locked» уже
после проделанной работы. IMMEDIATE заставляет ждать на входе.

В PostgreSQL ту же роль играют уровни изоляции и SELECT FOR UPDATE,
но рассуждение то же.

Проблема N+1
------------

Что это. Один запрос за списком, потом по одному запросу на каждый
элемент. На 50 заказах — 51 поход в базу, каждый со своим сетевым
временем.

Как увидеть. В проект встроен счётчик запросов, поэтому проблема
измеряется, а не обсуждается:

    python main.py nplus1

    НАИВНО  заказов: 30   запросов к базе: 31
    ПАЧКОЙ  заказов: 30   запросов к базе: 2

Как лечится. Строки всех заказов забираются одним запросом с IN
и раскладываются по заказам в памяти. В ORM это selectinload
или joinedload, механика та же.

Как не допустить повторно. Тест утверждает «ровно 2 запроса»
и ломается, когда кто-то добавит обращение к базе внутрь цикла. Замерять
время в таком тесте бессмысленно: оно нестабильно и зависит от машины,
а число запросов детерминировано.

Keyset-пагинация
----------------

Чем плох OFFSET. LIMIT 20 OFFSET 10000 заставляет базу прочитать
и выбросить 10000 строк: чем глубже страница, тем медленнее. Вторая
беда — сдвиг: если между запросами кто-то вставил запись, одна строка
покажется дважды, а другая пропадёт.

Как работает keyset. Страница берётся строго после известной
позиции:

    SELECT * FROM products
     WHERE (title, id) > (?, ?)
     ORDER BY title, id
     LIMIT ?

Сложность не зависит от глубины, сдвига не происходит. Цена — нельзя
прыгнуть на «страницу 50», только листать последовательно.

Две детали, о которых забывают:

  - сортировка по (title, id), а не только по title: title не уникален,
    при равных значениях порядок не определён, и строки начнут прыгать
    между страницами. Последним ключом сортировки всегда должно быть
    что-то уникальное;
  - берётся на одну запись больше, чем нужно: наличие «лишней» строки
    и есть признак того, что дальше что-то есть. Иначе понадобился бы
    отдельный COUNT(*) — второй проход по таблице.

Курсор непрозрачен для клиента (base64 от JSON). Это не про
безопасность, а про контракт: если клиенты научатся разбирать курсор,
поменять порядок сортировки без их поломки станет невозможно.

Устойчивость к отказам
----------------------

Ретраи с экспоненциальной задержкой. 0.1 → 0.2 → 0.4 → 0.8.
Постоянная задержка плоха тем, что при перегрузке получателя все клиенты
продолжают долбить его с прежней частотой и не дают встать.

Джиттер — случайная добавка к задержке. Без него тысяча клиентов,
упавших одновременно, повторит попытку тоже одновременно и положит
сервис повторно.

Повторять нужно не всё. Ошибку валидации повторять бессмысленно:
она детерминирована и повторится ровно так же. Список повторяемых
исключений задан явно.

Circuit breaker. Ретраи помогают при одиночном сбое, но делают хуже,
когда сервис лежит целиком: каждый клиент тратит таймауты, держит потоки
занятыми и падает сам. Предохранитель после N ошибок подряд размыкается
и отвечает ошибкой мгновенно, не трогая упавший сервис. Через заданное
время пропускает одну пробную попытку.

Как это тестируется без ожидания. Функция сна и часы передаются
параметрами, в тестах подменяются заглушками. Тест на четыре попытки
с задержками отрабатывает мгновенно. Тест, который спит три секунды,
перестают запускать — а значит, он бесполезен.

Кэш
---

Почему свой, а не functools.lru_cache. У lru_cache нет срока
жизни: протухшее значение отдаётся до перезапуска процесса.

Что кэшируется, а что нет. Карточка товара — да. Остаток — нет:
он меняется каждым заказом, и закэшированное значение почти сразу
становится ложью. При оформлении заказа остаток всегда читается из базы.

Общее правило: кэшировать можно то, что меняется редко и где цена
ошибки невелика. Данные, на основании которых принимаются решения
о деньгах и остатках, читаются напрямую.

Страницы каталога не кэшируются: ключом был бы курсор, а курсоров
столько же, сколько позиций. Кэш раздуется, попаданий почти не будет —
типичный случай, когда кэш только вредит.

Обработка ошибок
----------------

Доменные исключения (errors.py) не знают про HTTP. Код ответа —
атрибут исключения, а перевод в HTTP собран в одном обработчике:

    @app.exception_handler(ShopError)
    async def handle_shop_error(request, exc):
        return JSONResponse(status_code=exc.http_status, content=exc.as_dict())

Альтернатива — try/except в каждой ручке: много одинакового кода,
и рано или поздно где-то забудут, а клиент получит 500 вместо 409.

Добавить новый тип ошибки здесь — значит просто объявить класс.

ЧАСТЬ 4. HTTP API
==============================================================================

Поднять: python main.py serve, документация на
http://localhost:8000/docs.

  метод  путь                    что делает
  -----  ----------------------  -----------------------------------------
  GET    /v1/products            каталог, keyset-пагинация (limit, cursor)
  GET    /v1/products/{id}       карточка товара
  POST   /v1/orders              создать заказ (заголовок Idempotency-Key)
  POST   /v1/orders/{id}/cancel  отменить заказ, вернуть остатки
  GET    /healthz                процесс жив
  GET    /readyz                 готов принимать трафик

Пример:

    curl -X POST http://localhost:8000/v1/orders \
         -H "Content-Type: application/json" \
         -H "Idempotency-Key: order-2026-001" \
         -d '{"customer_id": 1, "items": [{"product_id": 1, "quantity": 2}]}'

Коды ответов:

  код  когда
  ---  ------------------------------------------------------
  201  заказ создан
  404  товар или заказ не найден
  409  не хватает товара или конкурентное изменение
  422  некорректный запрос или конфликт ключа идемпотентности
  502  внешний сервис недоступен
  503  сервис ещё прогревается

healthz и readyz разведены намеренно. «Процесс жив» и «готов
принимать трафик» — разные вещи: во время прогрева процесс жив, но
работать не может, и балансировщик не должен слать на него запросы.

==============================================================================
ЧАСТЬ 5. ТЕСТЫ
==============================================================================

    python main.py test

280 тестов, доли секунды. Без PostgreSQL — 263 и 17 пропущенных:
те, что требуют настоящей базы.

  файл                 что проверяет
  -------------------  ----------------------------------------------
  test_concurrency.py  гонки: 20 потоков, оверселлинг, откат резервов
  test_orders.py       валидация, идемпотентность, отмена, деньги
  test_db_patterns.py  N+1 по счётчику, пагинация, транзакции
  test_reliability.py  ретраи, предохранитель, кэш

Принципы, по которым они написаны
---------------------------------

Тесты на конкурентность запускают настоящие потоки. Гонка
не воспроизводится в один поток и не видна при ручной проверке.
threading.Barrier выстраивает потоки на одном старте — без него они
разойдутся по времени и гонки может не случиться, тест станет
«мигающим».

Плохое поведение закрепляется тестом намеренно. Есть тест, который
проверяет, что наивная реализация действительно оверселлит. Без него
утверждение «атомарный UPDATE нужен» остаётся словами.

Производительность проверяется счётчиком запросов, а не временем.
Время нестабильно, число запросов детерминировано.

Время и сон подменяются. Ни один тест не ждёт по-настоящему.

Проверяются инварианты, а не только результат. Например: «успешные
заказы + остаток = исходное количество». Это сильнее, чем считать только
успехи: ловит и оверселлинг, и потерянные резервы.

==============================================================================
ЧАСТЬ 6. ЧАСТЫЕ ВОПРОСЫ
==============================================================================

Какой файл запускать? main.py.

Нужна ли установка? Нет, ядро на стандартной библиотеке. Для тестов
нужен pytest, для HTTP — FastAPI.

Почему sqlite, а не PostgreSQL? Чтобы проект запускался сразу после
распаковки. Все приёмы — атомарный UPDATE, RETURNING, транзакции,
keyset-пагинация, индексы — переносятся на Postgres один в один.

Почему нет SQLAlchemy? Сырой SQL здесь нагляднее: видно, какой
именно запрос уходит в базу. В рабочем проекте ORM экономит время,
но ровно те же проблемы (N+1, блокировки, пагинация) в ней никуда
не деваются, только прячутся за абстракцией.

Почему деньги целым числом? 0.1 + 0.2 != 0.3. На тысячах операций
расхождение попадает в отчёты.

Зачем хранить цену в строке заказа? Цена в каталоге меняется, а заказ
должен помнить, по какой его оформили. Иначе вчерашние заказы
пересчитаются при изменении прайса.

Что будет, если убрать RETURNING? Вернётся баг с rowcount:
под конкуренцией сервис перестанет понимать, прошёл резерв или нет.
Есть запасной путь через блокировку соединения — для sqlite старее 3.35.

==============================================================================
ЧАСТЬ 7. POSTGRESQL И ВИТРИНА
==============================================================================

Запуск магазина
---------------

    pip install -e ".[serve,postgres]"
    docker compose up -d db
    
    python main.py pg --write-env   # строка подключения в .env
    python main.py migrate          # схема
    python main.py seed             # каталог
    python main.py shop             # магазин на localhost:8000

Без DATABASE_URL всё работает на sqlite, и магазин тоже полноценный:
python main.py shop создаёт файл shop.sqlite3, при первом запуске сам
заливает каталог, и заказы переживают перезапуск. Postgres нужен не ради
«настоящести», а ради того, что даёт сервер: пул соединений, миграции,
уровни изоляции, FOR UPDATE, планы запросов, одна база на несколько
приложений.

Временная база осталась только у демонстраций (race, nplus1,
pages): им нужны свои условия и чистый старт каждый раз.

Откуда берётся строка подключения
---------------------------------

Настройка подключения обязана жить вне кода: одна и та же сборка должна
уметь ходить и в локальную базу, и в продовую, а строка содержит пароль
и не должна попадать в репозиторий. Канонический способ — переменная
окружения:

    export DATABASE_URL=postgresql://shop:shop@localhost:5432/shop   # Linux, macOS
    set DATABASE_URL=postgresql://shop:shop@localhost:5432/shop      # Windows cmd
    $env:DATABASE_URL="postgresql://shop:shop@localhost:5432/shop"   # PowerShell

Но задать переменную окружения так, чтобы её увидела IDE, — отдельное
упражнение, особенно на Windows. Поэтому рядом поддерживается файл
.env в корне проекта: его правят обычным текстом.

    DATABASE_URL=postgresql://shop:shop@localhost:5432/shop

Приоритет — окружение, потом .env, потом sqlite по умолчанию.
Именно в таком порядке: иначе забытая строчка в файле будет молча
перебивать то, что задано при запуске, и человек будет чинить не ту
базу. Разбор — в env_file.py, формат намеренно минимальный (KEY=value,
решётка — комментарий, кавычки снимаются) и без подстановки переменных:
.env это данные, а не скрипт. Сам файл — в .gitignore.

Читают его два места: main.py при старте и factory.make_backend.
Второе обязательно, потому что main.py shop запускает uvicorn
отдельным процессом, и тот про разбор аргументов родителя ничего
не знает.

Команда pg: диагностика вместо угадывания
-----------------------------------------

    python main.py pg

Проверяет по шагам и говорит, что именно не так:

    1. Драйвер psycopg      установлен / нет -> команда установки
    2. DATABASE_URL         задан, и откуда: окружение или .env
    3. Сервер базы          отвечает / текст ошибки + docker compose up -d db

Команда ничего не чинит молча — с флагом --write-env она только
создаёт .env со строкой по умолчанию. Строка подключения печатается
с замаскированным паролем (_mask): она попадает и в логи, и в чужие
скриншоты.

Почему это отдельная команда, а не автоподключение: «не работает
с базой» — самая частая проблема при запуске чужого проекта, и разница
между «нет драйвера», «не задана строка» и «сервер не поднят» решается
разными действиями. Сообщение connection refused этой разницы
не объясняет.

Как убедиться, что база настоящая
---------------------------------

Купить товар на витрине, остановить сервер (Ctrl+C), запустить снова
и открыть страницу. На PostgreSQL остаток останется уменьшенным,
а заказ будет на месте. На sqlite-версии каталог вернётся к исходному:
база временная и удаляется вместе с процессом.

Как устроен выбор базы
----------------------

Репозиториев два, а сервисы у них общие:

    services/orders.py     ← бизнес-логика, не изменилась ни на строку
            ↓
    repositories/
      sqlite_repo.py       ← ? плейсхолдеры, соединение на поток
      postgres_repo.py     ← %s плейсхолдеры, пул соединений

Выбор происходит в factory.py:

    DATABASE_URL задан  ->  PostgreSQL
    не задан            ->  sqlite

Это и есть практический смысл разделения слоёв: смена базы — написать
второй репозиторий, а не переписать приложение.

Что добавилось вместе с Postgres
--------------------------------

Пул соединений. Открытие соединения к Postgres — это TCP-рукопожатие,
аутентификация и запуск процесса на сервере, десятки миллисекунд.
На каждый запрос так делать нельзя, поэтому пул держит готовые
соединения. В sqlite соединение стоило почти ничего, и хватало
threading.local.

Миграции. migrations/001_initial.sql, 002_product_media.sql
и маленький runner (migrate.py). Механика любой системы миграций:
файлы пронумерованы и применяются по порядку, таблица в базе помнит
применённые, каждая идёт в своей транзакции, применённые не правят.

Контрольные суммы проверяются: если применённый файл изменили, runner
откажется работать. Иначе схема на разных стендах разъедется молча.

ON CONFLICT DO NOTHING — атомарная вставка по ключу идемпотентности
без гонки и без исключения. Тонкость, на которой это упало при первом
запуске: индекс ЧАСТИЧНЫЙ (WHERE idempotency_key IS NOT NULL),
и Postgres требует повторить условие в ON CONFLICT. Без него:

    there is no unique or exclusion constraint matching
    the ON CONFLICT specification

Причина: частичных индексов по одной колонке может быть несколько,
и база не угадывает, какой имелся в виду.

SELECT ... FOR UPDATE — альтернатива атомарному UPDATE. Блокирует
строку до конца транзакции: конкурент ждёт на чтении, а не проигрывает
на записи. Работает, но держит блокировку дольше. В проекте есть оба
варианта и тест на каждый.

EXPLAIN ANALYZE. Метод db.explain() показывает план выполнения.
Тест проверяет, что keyset-пагинация действительно использует индекс:

    Limit
      ->  Index Scan using idx_products_title_id on products

Это сильнее замера времени: на маленькой таблице разницы во времени
не будет, а план покажет, читается индекс или вся таблица.

Ограничения на уровне схемы. CHECK (stock >= 0) не даст записать
отрицательный остаток, даже если логика ошибётся. ON DELETE RESTRICT
не даст удалить товар, на который ссылаются заказы: история важнее
удобства чистки каталога.

Типы. BIGINT GENERATED ALWAYS AS IDENTITY вместо SERIAL —
стандарт SQL и защита от случайной вставки в ключ. TIMESTAMPTZ,
а не TIMESTAMP: без таймзоны время теряет смысл, как только появляется
второй сервер. Деньги — BIGINT в копейках.

Витрина
-------

Одностраничный магазин: src/shopapi/web/ — три файла, без сборки
и без фреймворка. Отдаётся тем же приложением, поэтому нет ни отдельного
фронтенд-сервера, ни CORS.

  файл        что внутри
  ----------  ----------------------------------------
  index.html  разметка: шапка, герой, каталог, корзина
  app.css     оформление, тёмная тема, адаптив
  app.js      состояние, запросы к API, отрисовка

Состояние в одном объекте, отрисовка от него — тот же принцип, что
во фреймворках, только руками. Обработчики навешаны делегированием
на document: карточки перерисовываются, и вешать слушатели заново
пришлось бы каждый раз.

Что витрина показывает про бэкенд:

  - купил товар — остаток в карточке уменьшился, потому что изменился
    в базе;
  - нажал «Оформить» дважды — заказ один: ушёл ключ идемпотентности;
  - взял последний экземпляр — карточка гаснет, кнопка выключается;
  - ошибка «нет в наличии» приходит с сервера как 409 out_of_stock
    и показывается человеческим текстом;
  - обновил страницу — заказы на месте, они в PostgreSQL.

Баги, которые нашлись при сборке витрины
----------------------------------------

* Витрина работала только на одной из двух баз

Самый показательный баг проекта, и рассказывать на собеседовании стоит
именно его.

Ручки каталога — list_all, categories, get_full, recent —
я написал в постгресовом репозитории и не написал в sqlite-версии.
Приложение при этом поднималось без единой ошибки: /healthz
зелёный, /readyz зелёный, сервер слушает порт. Падало оно в момент
первого запроса каталога:

    AttributeError: 'SqliteProductRepository' object has no attribute 'list_all'

То есть ошибка ждала не разработчика, а пользователя.

Почему это не поймал Python. «Оба класса реализуют один интерфейс» —
в динамическом языке это утверждение, а не факт: методов просто нет,
пока кто-нибудь их не позовёт. Ни импорт, ни линтер, ни старт приложения
этого не замечают.

Почему это не поймали тесты. Тесты бизнес-логики ходили в sqlite,
тесты витрины — в Postgres. Каждый набор был зелёным на своей базе,
и ровно в стыке между ними никто не смотрел.

И два места специально маскировали разрыв:

    if not hasattr(repo, "recent"):        # витрина молча показывала
        return {"items": [], "total": 0}   # «заказов нет» вместо ошибки
    
    try:                                    # загрузчик каталога молча
        repo.add(..., description, category, emoji)
    except TypeError:                       # заливал товары без описаний
        repo.add(...)

Обе конструкции писались как страховка, а сработали наоборот:
превратили падение в тихо неверное поведение. Падение чинят в тот же
день; «почему-то нет описаний» живёт месяцами. Плюс except TypeError
вокруг вызова проглотил бы TypeError откуда угодно изнутри
репозитория — включая настоящую ошибку в SQL-слое.

Что сделано. Обе страховки убраны. В sqlite-репозитории дописаны
недостающие методы, в схему добавлены колонки description,
category, emoji (в PostgreSQL их приносила миграция 002).
Проверка вынесена в tests/test_storefront.py:

    @pytest.mark.parametrize("name", PRODUCT_API)
    def test_sqlite_product_repo_has_storefront_method(name):
        assert hasattr(SqliteProductRepository, name)
    
    
    def test_repositories_agree_on_signatures():
        ours = inspect.signature(getattr(SqliteProductRepository, name))
        theirs = inspect.signature(getattr(PgProductRepository, name))
        assert list(ours.parameters) == list(theirs.parameters)

Одинаковых имён мало — сравниваются и параметры: если у одной
реализации add без описания и категории, вызов из загрузчика упадёт
на TypeError. Важная деталь: этот тест не требует поднятого
PostgreSQL. Классы достаточно импортировать, подключение для сравнения
сигнатур не нужно, — значит расхождение ловится сразу у любого, а не
когда-нибудь на стенде с базой.

Вывод, который из этого следует. Абстракция «две реализации одного
интерфейса» не бесплатна: она держится ровно до тех пор, пока кто-то
её проверяет. Либо ABC с @abstractmethod, либо Protocol с проверкой
типов, либо — как здесь — тест. Чего точно нельзя, так это полагаться
на дисциплину и добавлять hasattr там, где метод обязан быть.

* LOWER() в sqlite не знает кириллицы

Поиск по каталогу оказался регистрозависимым: «Консоль» не находилась
по запросу «консоль». Встроенные LIKE и LOWER в sqlite приводят
регистр только у латиницы — Unicode-таблиц в стандартной сборке нет
(с ICU есть, но рассчитывать на неё нельзя: в Python её не бывает).

Решение — своя функция в соединении:

    conn.create_function("pylower", 1, lambda s: s.lower() if s else s,
                         deterministic=True)

Внутри обычный str.lower, который знает Unicode целиком. Флаг
deterministic=True разрешает базе использовать функцию в индексных
выражениях и кэшировать результат.

В PostgreSQL проблемы нет вовсе: ILIKE работает по правилам локали.
Это и есть цена «одинакового поведения на двух базах» — одинаковый SQL
ещё не значит одинаковый результат.

* Дата заказа выглядела по-разному на двух базах

PostgreSQL отдаёт datetime (тип TIMESTAMPTZ), sqlite — строку ISO:
отдельного типа даты у него нет. Витрина показывала то 13.09.2026 14:21,
то 2026-09-13T14:21:03.585846+00:00. Приведение к одному виду
вынесено в _format_time в HTTP-слое: разница в хранении не должна
доходить до интерфейса.

* Заголовки терялись в обёртке fetch

Написано было так:

    fetch(url, {
      headers: { 'Content-Type': 'application/json', ...options.headers },
      ...options,       // ← затирает headers целиком
    })

Спред options идёт ПОСЛЕ и перезаписывает собранный объект заголовков.
Запрос уходил как text/plain, сервер отвечал 422. Через curl всё
работало, потому что там заголовок ставился руками — классический случай
«у меня работает».

* Атрибут hidden не работал

  У кнопки стоял display: grid,
а он перебивает hidden. Крестик в поиске и счётчик пустой корзины
оставались видимыми. Лечится одним правилом:
[hidden] { display: none !important; }.

* Карточки не выравнивались по нижнему краю

  У описания стояли
и flex: 1, и обрезка в две строки — растяжение флекс-элемента
перебивает ограничение по строкам. Цены в соседних карточках
оказывались на разной высоте. Выравнивание делает margin-top: auto
у подвала карточки.

* Случайный цвет обложки давал кислотные сочетания

  Оттенок брался
из хеша артикула, и рядом оказывались ядовито-розовый и салатовый.
Заменено на подобранную вручную палитру из шести пар: выбор всё так же
устойчив по хешу, но из заведомо приличного набора.

Команды для работы с базой

    python main.py migrate --status   # что применено, что нет

Команды работают и с sqlite, и с PostgreSQL — выбор по DATABASE_URL.

Тесты против настоящей базы

==============================================================================
ЧАСТЬ 8. РАЗДЕЛЫ САЙТА, КАТАЛОГ И ОТЗЫВЫ
==============================================================================

Пять разделов и один HTML
-------------------------

Сайт состоит из разделов: каталог, отзывы, доставка, контакты,
о проекте. Файл при этом один — web/index.html, в нём пять блоков
<div class="page" data-page="...">, и роутер показывает нужный.

Переключение сделано на History API, а не на якорях #reviews.
Разница практическая:

  - ссылку можно прислать, и она откроет нужный раздел;
  - работают «назад» и «вперёд» в браузере;
  - адрес видно в строке, его можно скопировать.

Чем за это платит сервер
------------------------

Пока человек ходит по сайту, запросов к серверу нет: роутер меняет
адрес через history.pushState и показывает другой блок. Но стоит
нажать F5 на /reviews — и браузер честно спросит этот путь у сервера.

Без обработчика ответом будет 404. Это классическая поломка
одностраничных приложений, и коварна она тем, что не воспроизводится
при обычном хождении по сайту: находит её пользователь, который
обновил страницу или открыл присланную ссылку.

Поэтому в api.py есть ручка, отдающая ту же страницу на каждый
адрес раздела:

    PAGES = {"catalog", "reviews", "delivery", "contacts", "about"}
    
    @app.get("/{page}", include_in_schema=False)
    async def storefront_page(page: str):
        if page not in PAGES:
            return JSONResponse(status_code=404, content={...})
        return FileResponse(WEB_DIR / "index.html")

Список разделов задан явно, а не «отдаём index.html на всё подряд».
Иначе опечатка в ссылке молча покажет главную, поисковик
проиндексирует десяток дублей одной страницы, а сломанную ссылку
никто не заметит.

Порядок объявления маршрутов
----------------------------

Здесь проект наступил на настоящую ошибку, и она стоит отдельного
разбора, потому что вопрос про неё — хороший вопрос на собеседовании.

/{page} подходит под ЛЮБОЙ односегментный путь: /reviews, но также
/healthz и /readyz. FastAPI подбирает маршрут перебором в порядке
объявления и берёт первый подошедший. Пока ручка страниц стояла выше
проб, пробы получали 404.

В проде последствие тяжёлое: балансировщик считает живой сервис мёртвым
и снимает его с трафика. При этом приложение поднимается, витрина
работает, в логах чисто.

Правило: маршрут с параметром в корне пути опасен, и место ему в самом
конце. Ниже него — только монтирование статики, по той же причине.

Поймал тест:

    def test_api_paths_are_not_swallowed_by_page_route(client):
        assert client.get("/api/products").status_code == 200
        assert client.get("/docs").status_code == 200
        assert client.get("/healthz").json() == {"status": "ok"}

Каталог: платформы и справочные поля
------------------------------------

У товара появились platform, genre, developer, year. Платформа
стала фильтром витрины, поэтому под неё есть индекс:

    CREATE INDEX idx_products_platform ON products (platform);

Фильтры складываются через AND и собираются списком, а не склейкой
строк:

    clauses, params = [], []
    if category and category != "all":
        clauses.append("category = %s"); params.append(category)
    if platform and platform != "all":
        clauses.append("platform = %s"); params.append(platform)
    where = f"WHERE {' AND '.join(clauses)}" if clauses else ""

Значения уходят параметрами. Кавычка в поисковом запросе остаётся
кавычкой, а не становится SQL — про это спрашивают всегда.

Отдельная тонкость про поиск в sqlite: встроенные LIKE и LOWER
приводят регистр только у латиницы, поэтому «Консоль» не находилась
по «консоль». Лечится своей функцией в соединении — conn.create_function
с обычным str.lower, который знает Unicode целиком. В PostgreSQL
проблемы нет: ILIKE работает по правилам локали.

Отзывы
------

Новая таблица со связью на товары:

    CREATE TABLE reviews (
        id         BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
        product_id BIGINT      REFERENCES products (id) ON DELETE SET NULL,
        author     TEXT        NOT NULL CHECK (length(author) > 0),
        rating     SMALLINT    NOT NULL CHECK (rating BETWEEN 1 AND 5),
        body       TEXT        NOT NULL CHECK (length(body) > 0),
        created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
        is_demo    BOOLEAN     NOT NULL DEFAULT false
    );

Почему ON DELETE SET NULL, а не CASCADE. Отзыв о снятом
с продажи товаре — это всё ещё мнение покупателя о магазине. CASCADE
удалил бы его вместе с позицией каталога. Поэтому колонка NULLable,
и по той же причине в выборке стоит LEFT JOIN, а не INNER: с INNER
отзыв о магазине целиком молча исчез бы из выдачи.

Список — одним запросом. Названия товаров приходят джойном, а не
поиском в цикле: пятьдесят отзывов не должны стоить пятьдесят один
запрос. Это проверено счётчиком в тесте.

Сводка — одним проходом. Пять отдельных COUNT(*) прочитали бы
таблицу пять раз:

    -- PostgreSQL
    COUNT(*) FILTER (WHERE rating = 5) AS stars5
    -- sqlite: FILTER нет, поэтому
    SUM(CASE WHEN rating = 5 THEN 1 ELSE 0 END) AS stars5

Сортировка по дате, а не по id. Порядок вставки и дата отзыва
не совпадают. Второй ключ — id: без него отзывы, созданные в одну
секунду, меняются местами между запросами, и пагинация по такому
порядку показала бы один отзыв дважды.

Проверки в трёх местах. Pydantic-схема в HTTP-слое, функция
validate в репозитории, CHECK-ограничения в схеме базы. Это не
избыточность: схема отсекает мусор до бизнес-логики, функция даёт
человеку внятное сообщение вместо violates check constraint,
а база — последний рубеж, потому что клиент может быть и не наш.

Демонстрационные данные должны быть отличимы
--------------------------------------------

Отзывы в data/reviews.json выдуманы: магазина не существует,
покупателей нет. Каждый такой отзыв уходит в базу с флагом is_demo,
витрина этот флаг показывает, и удалить их можно одной командой:

    DELETE FROM reviews WHERE is_demo;

Это не украшение интерфейса. Демо-данные, которые невозможно отличить
от настоящих, — ловушка: рано или поздно кто-нибудь выгрузит таблицу
и предъявит её как мнения покупателей. Поэтому флаг проверяется тестом,
а отзыв, оставленный через форму, сохраняется БЕЗ него.

Даты при заливке разносятся по прошедшим неделям. Пятнадцать отзывов
с одинаковым временем до минуты — сразу видно, что данные
сгенерированы, и сортировку по дате на них не проверить.

Обложки товаров
---------------

scripts/make_art.py рисует SVG для каждого товара. Это собственная
графика: настоящие обложки игр и фотографии консолей принадлежат
издателям и производителям, и в проекте им не место — «некоммерческое
использование» этого не меняет, как и фанарт (у него свой автор
и всё те же защищённые персонажи).

Устройство генератора:

  - сцена по жанру — у шутера разломы и зарево, у приключения горы
    и сияние, у гонок трасса к горизонту, у файтинга арена
    в прожекторах;
  - палитра по платформе — синяя PlayStation, зелёный Xbox, красная
    Nintendo, фиолетовый PC: полку видно глазами, не читая подписей;
  - выбор устойчив — выводится из артикула через хеш, поэтому товар
    всегда выглядит одинаково, но соседние карточки не сливаются.

Слои идут от дальнего к ближнему: небо, светило, дальний план, средний,
ближний. Так строится любая постерная композиция, и так же она
читается взглядом.

Название и жанр в картинку НЕ впечатаны: они живут в карточке, где ими
управляет CSS сайта — один шрифт со всей витриной, нормальный перенос
длинных строк, масштабирование под ширину экрана. Текст внутри SVG
всего этого не умеет.

Векторный формат выбран не случайно: файл весит пару килобайт,
не мылится на экранах высокой плотности и правится текстом.

Тесты не должны трогать рабочую базу
------------------------------------

Тесты против PostgreSQL чистят таблицы перед каждым тестом. Первая
версия делала это прямо в базе из DATABASE_URL — и прогон pytest
вычищал каталог магазина. Разобраться тяжело: тесты зелёные, а товары
пропали.

Решение — отдельная схема:

    CREATE SCHEMA shopapi_test;
    ALTER DATABASE ... SET search_path TO shopapi_test, public;
    -- в конце
    DROP SCHEMA shopapi_test CASCADE;

Миграции создают там свой комплект таблиц, тесты работают с ними,
рабочие данные просто не видны.

Тонкость, на которую легко наступить: search_path задан для БАЗЫ,
а не для соединения. Пул открывает соединения по мере надобности,
и значение, выставленное на одном, не увидят остальные — тест ходил бы
то в тестовую схему, то в рабочую, в зависимости от того, какое
соединение досталось. Такую ошибку почти невозможно поймать: она
мигает.

==============================================================================
ЧАСТЬ 9. СТРАНИЦА ТОВАРА, ПРОФИЛИ И ПРАВО НА ОТЗЫВ
==============================================================================

Один ответ вместо шести
-----------------------

Страница товара показывает сразу всё: описание, характеристики, оценку
с распределением по звёздам, отзывы и рекомендации. Данные приходят
одним запросом:

    GET /api/products/by-sku/PS5-GOW18
      -> product, specs, reviews, rating, recommendations,
         can_review, already_reviewed

Шесть отдельных запросов дали бы шесть кругов по сети и страницу,
которая доезжает кусками и подпрыгивает по мере загрузки. Обратная
сторона — ответ тяжелее, и часть данных может быть не нужна. Здесь
это оправдано: страница показывает всё сразу, ничего не подгружая
по клику.

В адресе стоит артикул, а не числовой id: ссылка читается,
а id — деталь хранения, которой незачем торчать наружу.

Характеристики: почему JSON, а не таблица
-----------------------------------------

У консоли, игры и накопителя наборы характеристик не пересекаются
вообще. Классическое решение — таблица «атрибут — значение» (EAV) —
дало бы join и сортировку там, где нужно просто вывести список.

Поэтому характеристики лежат одной колонкой:

    ALTER TABLE products ADD COLUMN specs TEXT NOT NULL DEFAULT '{}';

Это осознанный размен, и у него есть граница. Как только понадобится
«показать все консоли с SSD от 1 ТБ», решение меняется: в PostgreSQL
это JSONB с GIN-индексом. Пока такой задачи нет, платить за неё
незачем.

Битый JSON не роняет страницу: _parse_specs ловит ошибку разбора
и возвращает пустой словарь. Товар покажется без таблицы — это лучше,
чем 500 на весь раздел.

Рекомендации одним запросом
---------------------------

Приоритет расставлен выражением в ORDER BY, а не двумя запросами
с объединением:

    SELECT * FROM products
     WHERE id <> %s
     ORDER BY (category = %s AND platform = %s) DESC,   -- та же полка
              (platform = %s) DESC,                      -- хотя бы платформа
              (stock > 0) DESC,                          -- то, что можно купить
              title
     LIMIT 4

Сам товар исключён: рекомендовать страницу саму на себя выглядит как
ошибка, потому что это она и есть. Товары без остатка уходят в конец —
советовать то, что нельзя купить, бессмысленно.

Рейтинги в каталоге: место, где N+1 возникает само
--------------------------------------------------

На карточке хочется показать звёзды. Напрашивается вызвать «сводку
по товару» в цикле отрисовки — и получить сорок четыре запроса вместо
одного. На тысяче позиций страница просто не откроется.

Поэтому рейтинги считаются пачкой:

    SELECT product_id, COUNT(*) AS total, AVG(rating) AS average
      FROM reviews
     WHERE product_id = ANY(%s)
     GROUP BY product_id

= ANY(%s) вместо IN (...): список уходит одним параметром, план
запроса не зависит от его длины, и база может его переиспользовать.
В тесте это закреплено счётчиком: на весь каталог не больше пяти
запросов, и число не растёт с числом товаров.

Отзыв только после покупки
--------------------------

Правило звучит просто, но важно, ГДЕ оно живёт. Кнопку на витрине
легко спрятать — и так и сделано, форма показывается только тому,
кто товар купил. Но это удобство, а не защита: POST на ручку отправит
кто угодно из консоли браузера.

Поэтому проверка стоит на сервере, и ответов три, а не один:

  код  когда                         что показывает витрина
  ---  ----------------------------  ----------------------------
  401  покупатель не выбран          «выберите профиль»
  403  выбран, но товара у него нет  «отзыв только после покупки»
  409  отзыв на этот товар уже есть  «вы уже оценили»

Разные коды нужны клиенту: на 401 предлагают войти, на 403 показывают
отказ, на 409 — существующий отзыв. Одним «нельзя» эти случаи
не различить.

Отзыв о магазине целиком (без товара) покупки не требует.

Один отзыв на товар — ограничением в базе
-----------------------------------------

    CREATE UNIQUE INDEX idx_reviews_one_per_customer
        ON reviews (customer_id, product_id)
     WHERE customer_id IS NOT NULL AND product_id IS NOT NULL;

Индекс ЧАСТИЧНЫЙ, и это существенно: без условия он запретил бы
второй отзыв о магазине (там product_id пустой), а таких отзывов
у человека может быть сколько угодно — заказы разные.

Проверять «сначала SELECT, потом INSERT» в коде нельзя по той же
причине, что и с ключом идемпотентности: два параллельных запроса
оба увидят, что отзыва нет, и оба вставят. Арбитром должна быть база,
а код переводит нарушение уникальности в понятную доменную ошибку.

Что считается покупкой
----------------------

    SELECT 1 FROM order_lines l
      JOIN orders o ON o.id = l.order_id
     WHERE o.customer_id = %s AND l.product_id = %s
       AND o.status <> 'cancelled'
     LIMIT 1

Две детали. Отменённый заказ покупкой не считается — товар вернулся
на склад, и иначе отзыв доставался бы бесплатно: заказать, написать,
отменить. LIMIT 1 — база останавливается на первой подходящей
строке вместо того, чтобы собирать всю историю покупок ради ответа
«да/нет».

Профили без выдуманной аутентификации
-------------------------------------

Настоящего входа в проекте нет. Форма с паролем, который ничего
не проверяет, — обман того, кто смотрит проект: выглядит как
аутентификация, а ею не является.

Поэтому механизм честный: список профилей из базы, выбранный
сохраняется в браузере и уходит заголовком:

    X-Customer-Id: 17

Заголовок, а не тело запроса: идентификатор относится к тому, КТО
делает запрос, а не к тому, что запрошено. В настоящем сервисе на этом
месте будет Authorization с токеном — место то же, меняется только
содержимое, и остальной код не изменится: он получает customer_id
и не знает, откуда тот взялся.

Функция называется current_customer именно поэтому: подменить
источник можно, не трогая ничего вокруг.

Демонстрационные данные
-----------------------

Отзывов 614 — по 11–17 на товар. Писать столько руками бессмысленно,
поэтому их собирает scripts/make_reviews.py из заготовок. Чтобы они
не выглядели копиями:

  - фраз в каждой группе много, берутся по две-три разные через sample
    (не choice: тот может выдать одну строку дважды);
  - заготовки разделены по категории и по оценке — у пятёрки и двойки
    общего текста быть не может;
  - часть фраз подставляет название, платформу или студию из каталога;
  - оценки распределены неравномерно, как в жизни: 56% пятёрок, 2%
    единиц. Равномерное распределение сразу выдаёт генератор;
  - даты разнесены по прошедшему году.

Зерно генератора фиксировано: перегенерация не переписывает файл
целиком, и в истории изменений видно только то, что реально менялось.

Всё это ВЫДУМАНО, и в базе помечено флагом is_demo — удаляется
одним запросом.

Два бага, которые нашлись при сборке
------------------------------------

* Роутер и загрузчик вызывали друг друга по кругу

Функция показа списка профилей сама переключала раздел, а переключение
раздела вызывало загрузку профиля, которая при отсутствии профиля
показывала список:

    showPage('profile') -> loadProfile() -> нет профиля
      -> renderCustomerPicker() -> showPage('profile') -> ...

Внешне страница работала — список всё-таки отрисовывался. Но пока
не приходил первый ответ, кеш оставался пустым, и каждый виток слал
новый запрос: 1467 обращений к /api/customers, пока браузер
не начал отклонять их с ERR_INSUFFICIENT_RESOURCES.

Нашлось не глазами, а счётчиком запросов в логе сервера после
браузерного прогона. Правило: функция либо навигирует, либо рисует.
Когда она делает и то и другое, взаимный вызов с роутером — вопрос
времени.

* «Последние N» использовались как «все»

Профиль определял, на какие товары покупатель уже написал отзыв,
фильтруя общий список list_recent(limit=200). Работало, пока отзывов
было меньше двухсот. На шестистах старые отзывы покупателя в окно
не попадали: профиль предлагал оценить уже оценённое, а сервер отвечал
409 на отправку.

Признак ошибки этого класса общий — выборка с лимитом, сделанная
для показа, используется в логике. Лечится отдельным запросом
reviewed_product_ids(customer_id), и закреплено тестом, который
создаёт 250 чужих отзывов поверх своего.

* Добавление в корзину пересобирало весь каталог

Обработчик вызывал renderGrid(), а тот перезаписывал innerHTML
всей сетки. Сорок три карточки исчезали и появлялись заново: браузер
перезапрашивал обложки, заново проигрывал анимацию появления,
прокрутка прыгала.

Это ровно та задача, которую во фреймворках решает сверка деревьев:
посчитать разницу и применить только её. Вручную она здесь занимает
десяток строк — refreshCard(id) меняет остаток и кнопку одной
карточки.

ЧАСТЬ 10. ВХОД, ПАРОЛИ И КЭШ

Что было не так раньше
----------------------

В предыдущей версии покупатель выбирался из списка, а его
идентификатор приходил заголовком X-Customer-Id. Это было честно
названо «не аутентификация», но у такого решения два последствия
посерьёзнее, чем неудобство:

  1. Представиться кем угодно можно было одной строкой в консоли.
      Заголовок ставит клиент. Заказ от чужого имени, отзыв о чужой
      покупке — всё это делалось подстановкой числа.
  2. Ручка /api/customers отдавала персональные данные. Имена,
      города и адреса почты всех зарегистрированных людей — любому,
      кто открыл сайт.

Обе вещи устранены: вход настоящий, а ручки со списком покупателей
больше нет.

Пароль не хранится
------------------

Хранится результат scrypt — функции, которую специально сделали
медленной и требовательной к памяти. Подбор по украденной базе
становится дорогим: на каждую попытку нужны те же десятки мегабайт
и то же время, что и при обычной проверке.

    hashlib.scrypt(password.encode(), salt=salt, n=2**14, r=8, p=1, dklen=32)

scrypt берётся из стандартной библиотеки — без внешних зависимостей.
Это не компромисс: реализация в OpenSSL нормальная. В рабочем сервисе
взял бы argon2id через argon2-cffi — он новее и лучше держит подбор
на видеокартах.

Соль у каждого своя. Одинаковые пароли дают разные хеши: радужные
таблицы бесполезны, и по базе не видно, у кого пароли совпадают.

Алгоритм записан ВНУТРЬ строки: scrypt$соль$хеш. Когда параметры
изменятся или scrypt заменят, старые хеши останутся проверяемыми,
а новые начнут писаться по-новому. Без этого смена алгоритма означает
сброс паролей у всех пользователей сразу.

Сравнение постоянное по времени — hmac.compare_digest, а не ==.
Обычное сравнение выходит на первом различающемся байте, и по времени
ответа значение подбирается посимвольно.

Одинаковый ответ на неверный вход
---------------------------------

    неверный пароль      -> 401 «неверный адрес или пароль»
    несуществующий адрес -> 401 «неверный адрес или пароль»

Разные сообщения превращают форму входа в проверялку
зарегистрированных адресов: подставляя почту, узнаёшь, кто есть в базе.

Одного текста мало. Для несуществующего адреса хеш всё равно
считается — иначе ответ приходит заметно быстрее, и существующие
адреса вычисляются секундомером ничуть не хуже.

Сессии
------

После проверки пароля выдаётся токен secrets.token_urlsafe(32).
secrets, а не random: второй предсказуем по нескольким значениям.

В базе лежит хеш токена, а не он сам. Утечка таблицы сессий
не даёт войти — из хеша токен не восстановить. Здесь хватает обычного
sha256 без соли и замедления: токен случайный и длинный, перебирать
его бессмысленно. Медленная функция нужна там, где секрет выбирает
человек.

Срок жизни ограничен тридцатью днями и проверяется В ЗАПРОСЕ:

    SELECT c.* FROM sessions s
      JOIN customers c ON c.id = s.customer_id
     WHERE s.token_hash = %s AND s.expires_at > now()

Проверять дату в Python — значит однажды забыть это сделать.
Просроченные записи вычищаются на старте: без уборки таблица растёт
вечно.

Токен уходит заголовком Authorization: Bearer ... — стандартным,
а не своим. Его понимают прокси и клиентские библиотеки. В адресе
токену не место: адреса целиком пишутся в журналы доступа, и сессия
утекает туда вместе с ними.

Личность берётся из сессии, а не из запроса
-------------------------------------------

    # было: клиент сообщает, кто он
    customer_id: int = Field(gt=0, default=1)   # в теле запроса
    
    # стало: сервер знает, кто он
    profile: dict = Depends(require_customer)   # из токена

Разница принципиальная: первое подделывается одной строкой.

require_customer — отдельная зависимость, а не проверка внутри
каждой ручки. Проверку, написанную вручную, легко забыть в одном
месте, и ручка молча начнёт работать для анонимов.

Отмена чужого заказа
--------------------

    existing = orders.get(order_id)
    if existing.customer_id != profile["id"]:
        raise NotFound("заказ не найден", order_id=order_id)

Без этой проверки отмена чужого заказа — перебор чисел в адресе.
Ошибка называется «небезопасная прямая ссылка на объект» и стабильно
попадает в списки самых частых: проверку прав забывают там, где
идентификатор выглядит безобидным числом.

404, а не 403 — намеренно. Ответ «доступ запрещён» подтверждает,
что такой заказ существует, и по кодам ответа перебором составляется
список существующих номеров.

Список «вы уже входили»
-----------------------

На форме входа показываются адреса, под которыми уже входили с этого
браузера. Хранится это в localStorage и только там — никаких
паролей, только адрес для подстановки в поле. Каждый вход всё равно
требует пароля.

Сам токен тоже лежит в localStorage, а профиль — нет: при загрузке
страницы витрина спрашивает /api/auth/me. Держать имя в браузере
и верить ему нельзя — его правит кто угодно через консоль.

Чего здесь нет
--------------

Ограничения частоты попыток входа. В рабочем сервисе на этой
ручке стоит счётчик неудач по адресу и по IP, иначе пароль подбирают
перебором. Здесь его нет: он требует общего хранилища счётчиков
и отдельного разговора про обход через прокси.

Восстановления пароля, подтверждения почты, двухфакторности.
Каждое — отдельная подсистема с почтовой рассылкой и одноразовыми
ссылками.

Всё это честнее назвать пробелами, чем делать вид, что их нет.

Кэш статики
-----------

Здесь была ошибка, которую видит только пользователь. Витрина
ссылалась на /static/app.css без версии, браузер честно клал файл
в кэш — и после обновления проекта показывал НОВЫЙ html со СТАРЫМ css.
Страница разъезжалась: разметка из свежей версии, стили из прошлой.
У разработчика при этом всё в порядке — он жмёт Ctrl+Shift+R
по привычке.

Решение из двух частей:

    /static/*  ->  Cache-Control: no-store, must-revalidate
    /          ->  Cache-Control: no-cache, must-revalidate
                 + /static/app.css?v=6.0.0 в ссылках

Обновил страницу — получил свежие css и js, без горячих клавиш.

Для рабочего сервиса это неправильно: файлы качались бы заново
на каждый заход. Там поступают наоборот — max-age=31536000, immutable
плюс версия в адресе: браузер не перепроверяет файл вообще, а обновление
приходит вместе с новым адресом. Версия в ссылках оставлена и здесь —
она страхует на случай прокси со своим кэшем, которому наш заголовок
не указ.

Порт
----

    python main.py shop --port 3000   # флаг
    SHOP_PORT=3000                    # .env
                                      # иначе 8080

Тот же порядок, что и у строки подключения: явное важнее настройки,
настройка важнее умолчания. Занятый порт проверяется ДО запуска
и объясняется словами с готовой командой — вместо `[Errno 98]
Address already in use` и стека вызовов, из которого человеку ничего
не следует.

==============================================================================
ЧАСТЬ 11. ВЫХОД В ИНТЕРНЕТ
==============================================================================

Проект перестал быть «запускается у меня на машине» и стал сайтом
по ссылке. Это отдельная работа, и на собеседовании про неё спрашивают
охотно: она показывает, что человек представляет себе не только код,
но и то, где этот код живёт.

Главная мысль всей части: окружение на хостинге не такое, как
на твоей машине. Порт назначаешь не ты. База создаётся пустой.
Клиент приходит через прокси. Файловая система стирается. Каждое
из этих отличий ломает что-то своё, и каждое здесь закрыто отдельно.

Почему sqlite не годится на хостинге
------------------------------------

Не потому, что «несерьёзно». Причина техническая: контейнер на хостинге
— расходный материал. Его пересобирают при каждом деплое, усыпляют
после простоя и будят на новой машине. Всё, что приложение записало
в свою файловую систему, при этом исчезает.

Файл shop.sqlite3 лежит внутри контейнера. Значит, заказы посетителей
живут ровно до следующего пробуждения сервиса. PostgreSQL — отдельный
сервер со своим диском, и его содержимое от судьбы контейнера
не зависит.

Отсюда же следует, что при таком устройстве нельзя ничего хранить
на диске приложения: ни загруженные картинки, ни логи, ни кэш. Всё,
что должно пережить перезапуск, уходит в базу или в объектное хранилище.

Порт задаёт хостинг
-------------------

    for name in ("SHOP_PORT", "PORT"):
        raw = os.environ.get(name, "").strip()

Хостинг сообщает порт переменной PORT и ждёт, что сервис сядет
именно на него: по этому порту он проверяет живость и через него
пускает трафик. Сервис, севший на свой любимый 8080, снаружи просто
не существует — проверка не проходит, деплой откатывается.

SHOP_PORT при этом главнее: PORT — слишком общее имя, оно может
оказаться в окружении от чего угодно постороннего, и настройка проекта
не должна молча уступать случайной переменной.

Рядом — грабли из Dockerfile:

    CMD ["sh", "-c", "exec python -m uvicorn ... --port ${PORT:-8080}"]

Exec-форма CMD ["python", "...", "--port", "$PORT"] переменные
не разворачивает: сервис получит строку $PORT вместо числа.
Поэтому форма с sh -c. exec перед командой нужен, чтобы uvicorn
стал процессом номер 1 и получал сигналы остановки напрямую, а не
через оболочку, которая их проглотит, — иначе контейнер не
останавливается вежливо, а убивается по таймауту.

За прокси адрес клиента приходит заголовком
-------------------------------------------

На хостинге запрос проходит через обратный прокси, и с точки зрения
приложения все посетители приходят с одного адреса — адреса прокси.
В логах это превращает разбор инцидента в бессмыслицу, а ограничитель
частоты — в общий счётчик на весь интернет: один активный человек
закроет вход всем остальным.

Настоящий адрес прокси кладёт в X-Forwarded-For. Но читать этот
заголовок можно только тогда, когда точно знаешь, что стоишь
за прокси: заголовок ставит кто угодно, и если доверять ему без
разбора, лимит обходится одной строкой. Поэтому доверие включается
переменной SHOP_TRUST_PROXY, и локально оно выключено.

* Ошибка, на которой ловятся почти все

Очевидное решение — взять первый адрес слева:

    first = forwarded.split(",")[0].strip()   # ТАК НЕЛЬЗЯ

Рассуждение выглядит правильным: прокси дописывают себя справа, значит
слева тот, кто пришёл снаружи. Оно и правда верно — ровно до момента,
когда клиент отправит заголовок сам.

Прокси не заменяют X-Forwarded-For, а дописывают в него свой
адрес, сохраняя присланное. Это общее поведение, а не особенность
одного хостинга: у Render оно прямо подтверждено в обсуждениях
поддержки — клиентское значение доходит до приложения нетронутым.

Значит, бот, отправивший X-Forwarded-For: 1.2.3.4, приходит
в приложение как:

    X-Forwarded-For: 1.2.3.4, <его настоящий адрес>

Код, берущий первый элемент, поверит подделке. И лимит — тот самый,
ради которого заголовок и читали, — обходится сменой одной строки
на каждый запрос.

* Как правильно

Считать справа, зная, сколько своих прокси стоит перед сервисом:

    index = max(len(parts) - max(hops, 1), 0)
    return parts[index]

При одном прокси настоящий адрес — последний в списке, при двух —
предпоследний. Всё, что левее, прислал клиент, и доверия этому нет.
Число прокси — настройка (SHOP_PROXY_HOPS), потому что зависит
от того, где стоит сервис, а не от кода.

Есть путь надёжнее, если периметр его даёт: некоторые (Cloudflare,
например) кладут адрес в собственный заголовок и перезаписывают
его, а не дописывают. Подделать такой снаружи нельзя. Он подключается
переменной SHOP_CLIENT_IP_HEADER и, если пришёл, используется вместо
разбора цепочки.

Как это нашлось. Первая версия брала первый элемент и выглядела
очевидно правильной. Ошибка всплыла при проверке документации
хостинга, где прямым текстом сказано, что присланный клиентом
заголовок сохраняется. Хороший пример того, почему «выглядит логично»
и «проверено» — разные вещи, особенно в безопасности.

База создаётся пустой
---------------------

На своей машине каталог заливают руками: python main.py seed.
На хостинге этого сделать некому — контейнер поднимается сам, и без
наполнения посетитель увидит витрину без товаров.

    def seed_if_empty(backend) -> int:
        if not catalog_is_empty(backend):
            return 0

Ключевое здесь — условие. Наполнение работает ровно один раз, пока
каталог пуст. Соблазн написать «заливать при каждом старте» большой:
так проще и всегда свежие данные. Цена — стёртые заказы и отзывы
посетителей при каждом пробуждении сервиса, а на бесплатном тарифе
оно случается по нескольку раз в день.

Ошибка наполнения не роняет сервис:

    except Exception:
        logger.exception("Не удалось наполнить базу при старте")

Витрина без каталога хуже витрины с каталогом, но лучше страницы
хостинга «сервис не запустился»: API живо, причина видна в логах,
чинить можно прицельно.

Демо должно оставаться живым
----------------------------

Товара в каталоге по 15–30 штук. Посетители покупают по-настоящему —
остаток уменьшается настоящим UPDATE. За сутки витрина превратится
в список «нет в наличии», и сайт будет выглядеть сломанным, хотя
работает ровно так, как задумано.

    sql = "UPDATE products SET stock = ? WHERE sku = ? AND stock < ?"

Фоновая задача раз в полчаса возвращает остатки к значениям из файла
каталога. Два решения внутри:

  - AND stock < ? — поднимаются только просевшие позиции. Если
    остаток больше, значит, его меняли осознанно, и уборка не имеет права
    это затирать.
  - Заказы не трогаются. Вместе с ними у человека пропало бы право
    оставить отзыв, которое он заслужил покупкой.

Сама задача — корутина, но работа с базой уходит в отдельный поток:

    await asyncio.to_thread(bootstrap.restock, backend)

Репозитории синхронные. Вызов их прямо в корутине заблокировал бы цикл
событий, и на время обновления остатков сервис перестал бы отвечать
всем посетителям сразу. Это общее правило для async-приложений: любой
блокирующий вызов внутри корутины останавливает не одну задачу,
а весь процесс.

И ещё одно, менее очевидное:

    task.cancel()
    with suppress(asyncio.CancelledError):
        await task

Отменённую задачу надо дождаться, а не просто пометить. Без await
отмена может не успеть отработать до закрытия пула соединений,
и в лог при остановке прилетит ошибка на ровном месте.

Открытые формы перебирают автоматически
---------------------------------------

Пока сервис живёт на localhost, ограничение частоты не нужно. Как
только у сайта есть публичный адрес, к нему приходят не только люди:
формы входа и регистрации перебирают ботами, а бесплатная база
на полгигабайта забивается мусорными профилями за вечер.

Алгоритм — скользящее окно: список отметок времени, из которого
выпадают старые.

    cutoff = now - rule.window_seconds
    while hits and hits[0] <= cutoff:
        hits.popleft()

Выбран он не потому, что самый хитрый, а потому, что самый честный.
У счётчика с фиксированным окном есть известная дыра на стыке:
10 запросов в конце минуты и 10 в начале следующей — это 20 запросов
за две секунды, формально не нарушивших лимит.

Три детали, за которые цепляются на собеседовании:

Проверка и списание — одна операция под замком. Разделить их
на «посмотреть» и «засчитать» — значит получить гонку, в которую
пролезут параллельные запросы: все прочитают счётчик до того, как
кто-то его увеличит, и все пройдут. Закреплено тестом на 300 потоках.

time.monotonic(), а не time.time(). Системные часы могут
прыгнуть назад — синхронизация NTP, перевод времени. Окно при этом
схлопнется или зависнет. Монотонные часы назад не идут.

Retry-After в ответе. Стандартный заголовок вместо «написано
в тексте ошибки»: его понимают клиентские библиотеки и умеют ждать
сами. Значение — время до освобождения места, а не целое окно:
иначе вежливый клиент прождёт вдвое дольше нужного.

Отдельно — блокировка на вход:

    "login": Rule(limit=10, window_seconds=300, block_seconds=300),

Без block_seconds перебор идёт со скоростью «лимит в окно»
бесконечно долго, что за ночь даёт заметное число попыток.
С блокировкой десять неудач стоят пятиминутной паузы.

Честное ограничение: счётчик лежит в памяти процесса. На одном
экземпляре этого достаточно, на нескольких счётчики разъедутся
и каждый начнёт пропускать свою долю. Правильное решение —
общий Redis с атомарным INCR; менять при этом придётся только
внутренности Limiter, интерфейс останется тем же. Это и есть смысл
того, что ограничитель — отдельный класс, а не пара строк в ручке.

И словарь ключей не должен расти вечно: каждый новый адрес — новая
запись, и без чистки это медленная утечка памяти. purge() вызывается
фоновой задачей, а не на каждом запросе — чистка под общим замком
на горячем пути стоила бы дороже, чем экономит.

Сайт открыт всем — значит, он обязан представиться
--------------------------------------------------

Магазин выглядит настоящим: цены, доставка, гарантия, отзывы.
Товары при этом не продаются, адреса вымышлены, а отзывы и профили
в каталоге сгенерированы скриптом.

Раньше про это было написано в разделах «Доставка» и «Контакты» —
то есть там, куда с главной никто не заходит. Теперь полоса
с предупреждением стоит в самой оболочке страницы и видна везде,
включая страницу товара, куда человек попадает по прямой ссылке.

Это не юридическая формальность, а то же требование, что и к любому
интерфейсу: человек должен понимать, что перед ним, до того, как
что-то нажмёт. Закреплено тестом по всем разделам — иначе полоса
однажды потеряется при правке вёрстки, и никто не заметит.

Образ работает не от root
-------------------------

    RUN useradd --create-home --uid 10001 app && chown -R app:app /app
    USER app

По умолчанию процесс в контейнере — root. Если в сервисе найдётся
дыра, она достанется хозяину контейнера. Отдельный пользователь
без прав ограничивает ущерб: выйти за пределы своей папки уже нельзя.

Рядом — PYTHONUNBUFFERED=1. Без него вывод оседает в буфере,
и логи хостинга показывают пустоту ровно до падения процесса.
Разбирать инцидент по логам, которых нет, невозможно.

Проверка живости
----------------

    healthCheckPath: /healthz

Без неё хостинг считает контейнер живым по факту запуска процесса —
то есть ещё до того, как приложение открыло пул соединений и готово
отвечать. Первые посетители в этот промежуток получают ошибку.

В проекте две разные ручки, и разница между ними — частый вопрос:

  - /healthz — жив ли процесс. Отвечает всегда, пока приложение
    работает. По ней перезапускают зависший контейнер.
  - /readyz — готов ли обслуживать. Ходит в базу. По ней решают,
    слать ли трафик.

Путать их дорого: если проверка живости ходит в базу, то временная
недоступность базы вызовет перезапуск всех экземпляров сервиса
разом — вместо того, чтобы просто подождать.

Чего в этой части сознательно нет
---------------------------------

  - Своего домена и HTTPS-сертификата. Хостинг выдаёт и то, и другое
    сам; настраивать вручную было бы демонстрацией ради демонстрации.
  - CDN для статики. Файлов мало, они мелкие, и на таком объёме CDN
    не окупает усложнения.
  - Метрик и трассировки. Просятся /metrics для Prometheus и
    OpenTelemetry, но без нагрузки и без места, куда их складывать, это
    были бы цифры ради цифр. Сквозной request_id в логах уже есть —
    это тот минимум, без которого нельзя.
  - Нескольких экземпляров сервиса. Бесплатный тариф даёт один,
    и весь код, который от этого зависит (кэш, счётчик частоты), помечен
    прямо в комментариях — вместе с тем, что надо будет поменять.
