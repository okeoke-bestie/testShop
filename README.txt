Демо: _<!-- сюда ссылку после деплоя: https://gameport.onrender.com -->_ ·

  | Витрина выдуманного магазина. Товары не продаются, оплата не
  | принимается, отзывы и профили в каталоге — сгенерированные тестовые
  | данные. Регистрация, заказы и отзывы при этом настоящие: они пишутся
  | в PostgreSQL и переживают перезапуск.

Работающий магазин: витрина в браузере, REST API и PostgreSQL под ними.
Товары добавляются в корзину, заказ сохраняется в базе, остатки
уменьшаются по-настоящему и переживают перезапуск.

Первый заход на бесплатном тарифе может занять около минуты: хостинг
усыпляет сервис после 15 минут без запросов и будит его обратно.

Проект собран вокруг задач, из которых реально состоит бэкенд,
а не вокруг CRUD: параллельные заказы на один товар, повторные запросы,
работа с базой без лишних обращений, устойчивость к отказам.

Запускать нужно main.py.

    python main.py           # меню
    python main.py shop      # магазин: витрина + API  ← начни с этого
    python main.py pg        # проверить готовность к PostgreSQL
    python main.py race      # гонка за последним товаром
    python main.py test      # 280 тестов (263 без PostgreSQL)

Витрина открывается на http://localhost:8080, документация API —
на /docs.
Порт меняется флагом --port или строкой SHOP_PORT в .env.

Быстрый старт с PostgreSQL
--------------------------

    pip install -e ".[serve,postgres]"
    docker compose up -d db
    
    python main.py pg --write-env   # создаст .env со строкой подключения
    python main.py migrate          # применить схему
    python main.py seed             # залить каталог из data/catalog.json
    python main.py shop             # открыть магазин

python main.py pg без аргументов ничего не меняет — только проверяет
по шагам: установлен ли драйвер, задана ли строка подключения и откуда
она взялась, отвечает ли сервер. Если что-то не так, печатает, что
именно сделать.

Строку подключения можно задать двумя способами:

    export DATABASE_URL=postgresql://shop:shop@localhost:5432/shop   # окружение
    echo 'DATABASE_URL=postgresql://shop:shop@localhost:5432/shop' > .env

Окружение важнее файла: забытая строчка в .env не должна молча
перебивать то, что задано при запуске. Сам .env — в .gitignore,
потому что в нём пароль.

Без DATABASE_URL проект работает на sqlite и не требует установки
вообще. Магазин при этом полноценный: python main.py shop создаёт
файл shop.sqlite3, сам заливает каталог при первом запуске, и заказы
переживают перезапуск. Разница с PostgreSQL не в «игрушечности», а в том,
что даёт настоящий сервер: пул соединений, миграции, уровни изоляции,
FOR UPDATE, планы запросов, работа нескольких приложений с одной базой.

Временная база остаётся только у демонстраций (race, nplus1,
pages): им нужны свои условия — товар с остатком 1, тридцать заказов,
двадцать пять позиций, — и чистый старт каждый раз.

Витрина
-------

Магазин без сборки и фреймворков: HTML, CSS и один файл на JavaScript.
Отдаётся тем же приложением, поэтому нет ни отдельного фронтенд-сервера,
ни CORS.

Разделы: каталог, страница товара, отзывы, доставка, контакты,
о компании, профиль. Переключаются через History API — без перезагрузки,
но с настоящими адресами: ссылку можно прислать, «назад» работает,
F5 не ломает страницу.

В каталоге: вкладки платформ (PlayStation 5, Xbox Series X|S,
Nintendo Switch, PC) и категорий, поиск по названию, описанию и студии,
шесть вариантов сортировки, оценки товаров, корзина, оформление
и отмена заказа, тёмная тема, адаптив до 360 пикселей.

Страница товара (/product/SKU) — описание, характеристики, оценка
с распределением по звёздам, все отзывы об этом товаре и рекомендации
похожего. Всё приходит одним ответом API: шесть отдельных запросов
дали бы шесть кругов по сети и страницу, которая доезжает кусками.

Профиль — регистрация, вход, заказы, покупки и то, что ещё можно
оценить. Вход настоящий: пароль хешируется scrypt со своей солью,
сессия живёт токеном 30 дней, а в базе лежит хеш токена, не он сам.
Заказы и отзывы принадлежат тому, кто вошёл: покупатель берётся
из сессии, а не из тела запроса.

* Откуда обложки

Их рисует scripts/make_art.py — это собственная графика, а не обложки
издателей. Настоящие обложки игр и фотографии консолей защищены
авторским правом, и в учебном проекте им не место; «некоммерческое
использование» этого не меняет.

Композиция выбирается по жанру, палитра — по платформе:

  жанр                         сцена
  ---------------------------  --------------------------------
  шутеры                       разломы, дым, зарево
  приключения и боевики        горы, туман, северное сияние
  гонки                        трасса, уходящая к горизонту
  ролевые и ужасы              мёртвый лес в тумане
  платформеры                  парящие острова
  файтинги                     арена в свете прожекторов
  космос и научная фантастика  планета с кольцом, звёздное поле
  консоли и аксессуары         подиум под направленным светом

Выбор устойчив: он выводится из артикула, поэтому товар всегда выглядит
одинаково. Названия игр, годы и студии в каталоге настоящие — это факты.
Цены, остатки и отзывы выдуманы.

* Что видно на витрине

Она показывает работу бэкенда наглядно:

  - купил товар — остаток в карточке уменьшился, потому что изменился
    в базе;
  - нажал «Оформить» дважды — заказ один, потому что ушёл ключ
    идемпотентности;
  - взял последний экземпляр — товар помечен «Нет в наличии» и кнопка
    выключена;
  - обновил страницу — заказы на месте, они в PostgreSQL.

Главная демонстрация
--------------------

На складе один экземпляр. Двадцать покупателей жмут «Купить»
одновременно:

    НАИВНО  (прочитали остаток -> проверили -> записали)
      продано экземпляров: 11   остаток: 0
      ОВЕРСЕЛЛИНГ: продали 11 шт., а был 1
    
    АТОМАРНО  (UPDATE ... WHERE stock >= ? одной командой)
      продано экземпляров: 1   остаток: 0
      корректно: один товар — один покупатель

Наивная версия читает остаток, проверяет и записывает. Между чтением
и записью вклиниваются другие потоки: все видят «остаток 1», все
проверяют, все списывают. Ошибка не воспроизводится в один поток
и всплывает в проде под нагрузкой.

Атомарная версия проверяет условие в момент записи, под блокировкой
строки:

    UPDATE products
       SET stock = stock - ?, version = version + 1
     WHERE id = ? AND stock >= ?
    RETURNING id

Тот же приём слово в слово работает в PostgreSQL и MySQL.

Две базы за одним интерфейсом
-----------------------------

Репозиториев два — sqlite_repo.py и postgres_repo.py, — а сервисы,
доменные модели и вся бизнес-логика у них общие и не изменились ни
на строку. Выбор базы происходит в одном месте (factory.py):

    DATABASE_URL задан  ->  PostgreSQL (пул соединений, миграции)
    не задан            ->  sqlite (временный файл, ноль зависимостей)

Читается он в одном месте (env_file.py) и с понятным приоритетом:
окружение -> .env -> sqlite по умолчанию. Настройка подключения
обязана жить вне кода: одна и та же сборка должна уметь ходить
и в локальную базу, и в продовую, а пароль не должен попадать
в репозиторий.

Ровно ради этого слои и разделены: «заменить базу» здесь означает
«написать второй репозиторий», а не переписать приложение.

Что появилось вместе с Postgres: пул соединений, миграции с контролем
контрольных сумм, ON CONFLICT для идемпотентности, `SELECT ... FOR
UPDATE как альтернатива атомарному UPDATE, EXPLAIN ANALYZE` для планов
запросов, внешние ключи и CHECK-ограничения на уровне схемы.

Архитектура
-----------

    web/              витрина: HTML, CSS, JS без сборки
       ↓
    api.py            HTTP: pydantic-схемы, request_id, обработка ошибок
       ↓
    services/         бизнес-логика: заказы, каталог
       ↓
    repositories/     доступ к данным, SQL
       ↓
    db.py             соединения, транзакции, счётчик запросов
       ↓
    models.py         доменные типы — не зависят ни от чего

Зависимости направлены строго вниз. Домен не знает ни про HTTP, ни про
базу, поэтому бизнес-логику можно вызвать из CLI, из фоновой задачи
и из теста — и тесты логики выполняются за миллисекунды без базы.

Решения и их обоснование
------------------------

Деньги в копейках целым числом. float для денег не годится:
0.1 + 0.2 != 0.3, и на тысячах операций расхождение попадает в отчёты.

Цена копируется в строку заказа. Не берётся по ссылке из каталога:
цена меняется, а заказ должен навсегда помнить, по какой его оформили.
Иначе вчерашние заказы пересчитаются при изменении прайса.

Уникальность ключа идемпотентности — в базе, а не в коде. Проверка
«сначала SELECT, потом INSERT» — это гонка: два параллельных запроса
оба увидят пустой результат. Арбитром должна быть база.

BEGIN IMMEDIATE вместо обычного BEGIN. Обычный BEGIN берёт
блокировку записи лениво, и конкурент проигрывает уже после того, как
проделал работу. IMMEDIATE заставляет ждать на входе.

Тот же ключ с другим телом запроса — ошибка, а не старый результат.
Молча вернуть прежний заказ нельзя: клиент просил другое и не заметит
подмены.

Баги, которые нашлись при разработке
------------------------------------

cursor.rowcount врёт при общем соединении. Первая версия
определяла успех резервирования по rowcount == 1. В один поток
работает; на тесте с 20 потоками база отработала верно (остаток ушёл
с 1 на 0, ровно одна строка изменена), но rowcount вернул ноль всем
двадцати потокам, включая победителя.

Причина: rowcount берётся из sqlite3_changes(), а эта функция
относится к соединению, не к курсору. Потоки работают через одно
соединение, их вызовы перемежаются, и значение успевает перезаписаться
чужим запросом.

Последствия были бы тяжёлыми: сервис решил бы, что резерв не прошёл,
откатил заказ — и списанный товар вернулся бы на склад, хотя покупатель
его купил. Или наоборот, при другом порядке.

Лечится переходом на UPDATE ... RETURNING: возвращаемая строка
принадлежит результату самого запроса и привязана к своему курсору.

Нашлось не глазами и не в один поток — только тестом на 20 потоках,
и первые прогоны были «мигающими»: тест то проходил, то падал. Мигающий
тест — это не повод его удалить, а сигнал, что в коде настоящая гонка.

Одно соединение sqlite на все потоки ломается. Первая версия
держала общее соединение (иначе :memory: даёт каждому потоку свою
пустую базу). На Linux и Python 3.11 это работало. На Windows
и Python 3.14 — падение с `sqlite3.InterfaceError: bad parameter
or other API misuse`: драйвер заметил порчу внутреннего состояния.

Показательно, что на других версиях оно могло не падать, а тихо
возвращать мусор — это хуже падения.

Причина того же класса, что и история с rowcount: состояние
соединения общее, а потоки об этом не знают. Решение — как в любом
настоящем сервисе: база одна (файл), соединение своё на каждый
поток. Режим :memory: оставлен для однопоточных сценариев,
и вызовы в нём выстраиваются в очередь, чтобы он не падал.

Витрина работала только на одной из двух баз. Ручки каталога
(list_all, categories, get_full, recent) были написаны в
постгресовом репозитории и не написаны в sqlite-версии. Приложение
поднималось без единой ошибки — и падало с AttributeError в момент
первого запроса каталога. То есть ошибка ждала не разработчика,
а пользователя.

Питон не проверяет «оба класса реализуют один интерфейс»: методов
просто нет, пока кто-нибудь их не позовёт. А два места специально
маскировали расхождение:

    if not hasattr(repo, "recent"):      # витрина молча показывала
        return {"items": [], "total": 0} # «заказов нет» вместо ошибки
    
    try:                                  # загрузчик каталога молча
        repo.add(..., description, category, emoji)
    except TypeError:                     # заливал товары без описаний
        repo.add(...)

Обе «страховки» сработали наоборот: они превратили падение в тихо
неверное поведение, которое никто не замечает. Убраны; вместо них
test_storefront.py перебирает методы обоих репозиториев и сравнивает
их сигнатуры через inspect.signature. Этот тест не требует поднятого
Postgres — классы для сравнения достаточно импортировать, а значит
расхождение ловится сразу, а не когда-нибудь на стенде с базой.

Попутно нашлось следствие того же разрыва: в схеме sqlite не было
колонок description, category, emoji — их добавляла только
миграция PostgreSQL.

LOWER() в sqlite не знает кириллицы. Поиск по каталогу оказался
регистрозависимым: «Консоль» не находилась по запросу «консоль».
Встроенные LIKE и LOWER в sqlite приводят регистр только у латиницы
(сборка с ICU это меняет, но её нет в стандартном Python). Решение —
зарегистрировать в соединении свою функцию: conn.create_function,
внутри обычный str.lower, который знает Unicode целиком. В PostgreSQL
проблемы нет: ILIKE работает по правилам локали.

Маршрут с параметром в корне съел пробы. Ручка @app.get("/{page}"),
отдающая страницы разделов, была объявлена раньше /healthz и /readyz.
FastAPI подбирает маршрут перебором в порядке объявления, а /{page}
подходит под любой односегментный путь — и пробы стали получать 404.

В проде это означало бы, что балансировщик считает живой сервис мёртвым
и снимает его с трафика. Приложение при этом поднимается, витрина
работает, в логах ничего.

Нашлось тестом test_api_paths_are_not_swallowed_by_page_route, а не
глазами. Лечится порядком: маршрут с параметром в корне объявляется
последним, ниже него — только монтирование статики.

Прогон тестов вычищал рабочую базу. Тесты против PostgreSQL чистили
таблицы перед каждым тестом — в той самой базе, что задана
в DATABASE_URL. После pytest каталог магазина оказывался пустым,
и понять причину было тяжело: тесты-то зелёные.

Решение — отдельная схема: CREATE SCHEMA shopapi_test, search_path
на неё, миграции создают там свой комплект таблиц, в конце схема
сносится одной командой. Рабочие данные тесты просто не видят.

Важная деталь: search_path задан для базы, а не для соединения. Пул
открывает соединения по мере надобности, и значение, выставленное
на одном, не увидят остальные — тест ходил бы то в тестовую схему,
то в рабочую, в зависимости от того, какое соединение досталось.

Добавление в корзину пересобирало весь каталог. Обработчик вызывал
renderGrid(), а тот перезаписывал innerHTML всей сетки. Сорок три
карточки исчезали и появлялись заново: браузер перезапрашивал обложки,
заново проигрывал анимацию, прокрутка прыгала.

Лечится тем, чем во фреймворках занимается сверка деревьев — поправить
ровно то, что изменилось. Здесь это refreshCard(id): остаток и кнопка
одной карточки, десяток строк.

Роутер и загрузчик вызывали друг друга по кругу. Функция показа
списка профилей сама переключала раздел, а переключение раздела
вызывало загрузку профиля, которая при отсутствии профиля показывала
список:

    showPage('profile') -> loadProfile() -> нет профиля
      -> renderCustomerPicker() -> showPage('profile') -> ...

Внешне страница работала: список всё-таки отрисовывался. Но пока
не приходил первый ответ, кеш оставался пустым, и каждый виток слал
новый запрос — 1467 обращений к /api/customers, пока браузер
не начал отклонять их с ERR_INSUFFICIENT_RESOURCES.

Нашлось не глазами, а счётчиком запросов в логе сервера после
браузерного прогона. Правило: функция либо навигирует, либо рисует;
когда она делает и то и другое, взаимный вызов — вопрос времени.

«Последние N» использовались как «все». Профиль определял, на какие
товары покупатель уже написал отзыв, фильтруя общий список
list_recent(limit=200). Работало, пока отзывов было меньше двухсот.
На шестистах старые отзывы в окно не попадали: профиль предлагал
оценить уже оценённое, а сервер отвечал 409.

Признак ошибки этого класса общий — выборка с лимитом, сделанная
для показа, используется в логике. Лечится отдельным запросом
reviewed_product_ids(customer_id).

Замыкание захватывает переменную, а не значение. В демонстрации
функция внутри цикла обращалась к product из внешней области. К моменту
запуска потоков цикл уже ушёл на следующую итерацию, и функция увидела
бы чужой товар. Поймал линтер (правило B023), исправлено передачей
значения через аргумент по умолчанию.

Установка
---------

    python main.py test                 # тесты — без установки, нужен только pytest
    pip install -e ".[dev]"             # pytest + линтер
    pip install -e ".[serve]"           # FastAPI, если нужен HTTP
    pip install -e ".[serve,postgres]"  # + psycopg для PostgreSQL
    python main.py shop                 # http://localhost:8080

Ядро не зависит ни от чего, кроме стандартной библиотеки. Это осознанное
решение: проект должен запускаться сразу после распаковки, а не после
получасовой установки.

Ограничения
-----------

Что честно не сделано:

  - Миграции — свой маленький runner, а не alembic. В рабочем проекте
    я бы взял alembic; здесь важнее показать механику, и она умещается
    в сто строк.
  - Сессии без refresh-токенов и без 2FA. Пароли солятся и хешируются
    scrypt, токен сессии хранится в базе только хешем, срок жизни —
    30 дней. Чего нет: обновления токена, подтверждения почты,
    восстановления пароля, второго фактора.
  - Нет нагрузочного теста. Корректность под конкуренцией проверена,
    пропускная способность — нет, поэтому никаких утверждений про RPS.
  - Кэш и счётчик частоты запросов — локальные, в памяти процесса.
    На одном экземпляре этого достаточно, на нескольких нужен общий
    Redis: иначе инвалидация не доходит до соседей, а лимит на вход
    каждый узел считает по-своему и пропускает свою долю попыток.
  - Модерации отзывов нет. На публичном демо любой текст виден сразу.
    Экранирование от XSS есть, проверки содержимого — нет.

Размещение в интернете
----------------------

    docker compose up --build     # то же, что поедет на хостинг
    # открыть http://localhost:8080

Пошаговая инструкция для бесплатного размещения (GitHub → Neon →
Render) — в ИНСТРУКЦИЯ_ДЕПЛОЙ.md.

Что добавлено ради публичного доступа:

    Что: PORT из окружения
    Зачем: хостинг сам назначает порт и проверяет, слушает ли сервис именно его

    Что: --proxy-headers
    Зачем: за обратным прокси адрес клиента приходит заголовком; без этого в логах у всех один адрес

    Что: healthCheckPath: /healthz
    Зачем: контейнер считается живым, когда отвечает приложение, а не когда запустился процесс

    Что: наполнение пустой базы при старте
    Зачем: база на хостинге создаётся чистой, залить каталог руками там некому

    Что: SHOP_AUTO_SEED только если база пуста
    Зачем: иначе каждое пробуждение сервиса стирало бы заказы и отзывы посетителей

    Что: восстановление остатков раз в полчаса
    Зачем: товара по 15–30 штук: за сутки витрина стала бы списком «нет в наличии»

    Что: лимит частоты на вход, регистрацию, заказ и отзыв
    Зачем: открытые формы перебирают автоматически; бесплатная база на 0.5 ГБ забивается мусорными профилями за вечер

    Что: полоса «демонстрационный проект» на всех страницах
    Зачем: сайт открыт всем и выглядит как настоящий магазин — это должно быть понятно сразу

    Что: образ работает не от root
    Зачем: дыра в сервисе достанется пользователю без прав
